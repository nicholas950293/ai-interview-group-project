## R-001：程式碼執行沙箱的隔離技術

**決策**：以 Docker 容器為執行單元，每種語言一個預先建置的最小映像檔，
每次執行啟動一個拋棄式容器。生產環境**應**搭配 gVisor（`runsc`）執行時期作為
第二層防護。

容器啟動參數必須固定包含：

| 參數 | 值 | 對應憲章原則 VI 條款 |
|------|-----|---------------------|
| `--network=none` | 無網路命名空間 | 禁止對外網路存取 |
| `--read-only` | 根檔案系統唯讀 | 禁止存取宿主檔案系統 |
| `--tmpfs /work` | 記憶體暫存工作目錄，含 `size`、`noexec` 例外處理 | 僅允許專屬暫存目錄 |
| `--memory` / `--memory-swap` | 512 MB / 512 MB（禁用 swap） | 記憶體上限 |
| `--cpus` | 1.0 + `RLIMIT_CPU` 10 秒 | CPU 時間上限 |
| `--pids-limit` | 64 | 程序數量上限 |
| `--cap-drop=ALL` | 移除所有 capability | 最低權限 |
| `--security-opt=no-new-privileges` | 禁止提權 | 不得具備提權能力 |
| `--user` | 非 root 的固定 UID | 最低權限 |
| `--rm` | 結束即刪除 | 用後即棄 |

牆鐘逾時由宿主端計時器強制 `kill`，不依賴容器內部自我約束。輸出以串流讀取
並於超過 1 MB 時截斷。

**理由**：Docker 是唯一同時滿足「五種語言皆有成熟映像檔」「上述六項隔離條件皆可
透過既有旗標宣告式達成」「隔離效果可用自動化測試驗證」三者的方案。憲章原則 VI 的
每一條款都能對應到具體且可斷言的容器參數——這對「安全關卡」的可測試性至關重要。

gVisor 列為建議而非強制，是因為它在部分 CI 環境不可用；缺少它時 Docker 的預設
seccomp 與上述旗標仍構成可接受的基準防護。

**已評估的替代方案**：

- **Firecracker microVM**——隔離最強（獨立核心），但需要 KVM 支援、開發者本機
  （尤其 Windows／macOS）難以執行，會使「安全關卡」測試無法在開發階段執行。
  以本專案 ≤50 人的規模而言，其營運複雜度不成比例。
- **nsjail / bubblewrap**——輕量且隔離良好，但需自行處理五種語言的執行環境準備，
  等於重造 Docker 映像檔管理。
- **Judge0 / Piston（現成評測引擎）**——開箱即支援多語言，可大幅縮短工期。
  否決原因是兩者皆為額外的長駐外部服務，其內部隔離設定不在我方控制與測試範圍內，
  而憲章原則 VI 要求我方能證明每一項隔離條件成立。若未來工期壓力升高，
  這是最值得重新評估的選項。
- **在應用程式行程內以語言層沙箱執行（如 VM2、RestrictedPython）**——直接否決。
  語言層沙箱有長期且反覆的逃逸紀錄，且無法滿足資源上限與網路隔離要求。

## R-002：資料存取路徑與 RLS 的實際生效機制

**決策**：

1. **前端不直連 Supabase**。所有資料存取一律經由 FastAPI。
   這消除了原 PRD 中「前端 REST Client 即時同步」與「後端 API 存取」兩條路徑
   並存所造成的權限模型分歧。
2. **內部使用者（HR／主管）的請求**：FastAPI 取得請求中的 Supabase JWT，
   以該 JWT 建立 PostgREST 連線。RLS 政策依 `auth.jwt()` 中的自訂 claim
   （`app_role`、`dept_id`）判定，權限由 PostgreSQL 強制執行。
3. **應徵者的 token 請求**：無 JWT 可用。改以 `SECURITY DEFINER` 的
   PostgreSQL 函式作為唯一入口，函式內部驗證 token 與效期，僅回傳該筆考核中
   應徵者可見的欄位。函式對 `anon` 角色授權，底層資料表不對 `anon` 開放。
4. **`service_role` 金鑰的使用範圍**：僅限資料庫遷移與排程維護作業，
   **不得**用於處理使用者請求。此限制須有測試守護。

**理由**：原 PRD 的 `current_setting('app.current_dept_id', true)` 是自訂 session
變數，需要有人在每個交易明確設定；而若後端以 `service_role` 連線，RLS 會被完全
繞過——該政策實際上不會提供任何保護。改用 `auth.jwt()` claim 後，權限判定的
輸入來自簽章過的 token，後端無從偽造，符合憲章原則 IV「必須在資料存取層強制執行」。

`SECURITY DEFINER` 函式是應徵者路徑的關鍵：它讓「憑 token 存取」這件事同樣落在
資料庫層，而非退化成應用程式層的 if 判斷。

**已評估的替代方案**：

- **維持自訂 GUC + 後端每交易 `SET`**——可行但脆弱：任何忘記設定的程式路徑
  都會靜默地取得全表存取權，且難以測試「忘記設定」這個失敗模式。
- **後端全程使用 `service_role` 並自行實作授權**——把權限判定從資料庫移到
  應用程式層，直接牴觸憲章原則 IV。
- **前端直連 Supabase + RLS**——可減少後端工作量，但 AI 呼叫與沙箱執行必須在
  後端進行，會形成兩套權限模型，且金鑰管理面擴大。

## R-003：HR 不可見 AI 報告與內部評語的實施方式

**決策**：將 `ai_reports` 與 `manager_decisions` 拆為獨立資料表，
以 RLS 政策限定僅同部門主管可讀；HR 角色的政策不涵蓋這兩張表。
HR 所需的決策結果另以 `assessments.final_decision` 欄位提供
（於決策寫入時同步更新），該欄位僅含結果列舉值，不含評語。

**理由**：FR-008 要求「HR 角色的查詢結果本身即不包含受限欄位」。若沿用原 PRD
把 `ai_report` 與 `manager_decision` 放在 `candidates` 表的 JSONB 欄位，
RLS 只能做到列級（row-level）過濾，無法做到欄位級隔離——HR 讀取該列時就會
一併取得受限內容。拆表後，隔離邊界與 RLS 的能力邊界一致，且可用越權測試驗證。

PostgreSQL 的欄位級 `GRANT` 是另一個可行機制，但 PostgREST 對欄位級權限的
錯誤回饋較不直觀，且無法與 RLS 政策統一表達。

**已評估的替代方案**：

- **單表 + 欄位級 GRANT**——可行，但權限規則散落在兩套機制（RLS 與 GRANT），
  審查與測試成本較高。
- **單表 + 後端過濾欄位**——牴觸 FR-008 與憲章原則 IV。

## R-004：前端技術選擇

**決策**：原生 JavaScript（ES2022 模組）+ Tailwind CSS CDN，不引入 React。

**理由**：PRD 明確把「Zero-Build Standard Stack」列為選型目標，而 React 在標準
用法下需要建置流程（JSX 轉譯）；兩者並列本身即為矛盾。本功能的前端為三個
角色各一組管理畫面加上一個作答頁面，狀態複雜度集中在程式碼編輯器元件，
而該元件無論選哪個框架都是引入既有的編輯器函式庫。憲章原則 III 要求
最小實作，在此情境下 React 帶來的收益不足以抵銷建置流程的成本。

程式碼編輯器採 CodeMirror 6，以 ES 模組方式自 CDN 載入。

**已評估的替代方案**：

- **React + CDN + Babel 瀏覽器端轉譯**——保留 React 寫法且無建置步驟，
  但每次載入都要轉譯，效能與除錯體驗皆較差。
- **React + Vite 建置**——違背 PRD 的 Zero-Build 目標。若日後畫面數量顯著增加，
  這是第一個該重新評估的決策。

## R-005：AI 服務的模型選擇與抽象層

**決策**：Gemini 模型 ID 由環境變數 `GEMINI_MODEL` 提供，程式碼中**不得**寫死。
所有 AI 呼叫置於 `AiProvider` 介面之後（契約見
[contracts/ai-provider.md](contracts/ai-provider.md)），實作與介面分離。

PRD 指定的 `gemini-3-flash-preview` 為預覽版模型 ID，**必須**在實作前
以實際 API 呼叫驗證其可用性、配額與速率限制，並確認其正式版遷移路徑。
若該 ID 不可用，改用當時可用的 flash 級模型，僅需變更環境變數。

**理由**：預覽版模型的 ID 與可用性會變動，把它寫進程式碼會製造一個必然發生的
維護債。介面抽象同時是憲章原則 II 的硬性要求——測試套件必須能在無外部服務的
情況下執行，因此 AI 呼叫本來就得可替換。

三種 AI 用途（出題、答題助教、評測）的提示詞（prompt）**必須**與程式邏輯分離，
存放於版本控管的獨立檔案，使其可被審查與調整而不需改動程式碼。

**已評估的替代方案**：

- **直接使用 `google-generativeai` SDK 而不加抽象層**——牴觸憲章原則 II。
- **同時支援多家 AI 供應商**——規格未要求，牴觸憲章原則 III 的最小範圍要求。

## R-006：非同步評測的執行方式

**決策**：提交後以 FastAPI 的 `BackgroundTasks` 觸發評測，評測狀態記錄於
`ai_reports` 資料表（`status`：`pending` / `success` / `failed`）。
沙箱執行以 `asyncio.Semaphore` 限制併發數為 10，超出者等候。
主管端以輪詢方式取得評測結果。

**理由**：SC-005 要求提交後 3 分鐘內可見報告，而規模上限為 50 位同時作答者，
每次評測包含數次沙箱執行加一次 AI 呼叫。這個負載不需要獨立的訊息佇列。
引入 Celery／Redis 會新增兩個長駐服務與一套部署複雜度，牴觸憲章原則 III。

失敗的評測留下 `failed` 紀錄而非消失，滿足 FR-059 的可重試要求；
重試由主管手動觸發，不做自動重試——自動重試在 AI 服務故障時會放大成本。

**已評估的替代方案**：

- **Celery + Redis**——正確但過重。若日後併發規模提升一個數量級，
  這是應該切換的目標架構，`AiProvider` 與沙箱介面的抽象已為此預留空間。
- **同步阻塞執行**——提交請求需等待數十秒，體驗不可接受且佔用連線。
- **WebSocket 即時推送**——增加連線管理複雜度，輪詢已足以滿足 3 分鐘的目標。

## R-007：Email 寄送服務

**決策**：透過 SMTP 寄送，連線參數（主機、埠、帳密、寄件者）全部由環境變數提供。
寄送邏輯置於 `EmailSender` 介面之後，測試以替身取代。

**理由**：PRD 未指定寄送服務。SMTP 是唯一不綁定特定供應商的選項——企業通常已有
可用的 SMTP 中繼，且 SendGrid、SES、Mailgun 等服務皆提供 SMTP 介面，
未來切換不需改動程式碼。

寄送失敗必須被捕捉並寫入 `assessments.email_status = 'FAILED'` 與失敗原因
（FR-071、FR-072），**不得**讓例外中斷請求。

**已評估的替代方案**：

- **Supabase 內建 Email**——僅為認證流程設計，不適合業務通知。
- **直接綁定 SendGrid API SDK**——增加一個不必要的相依與供應商鎖定。

## R-008：測試策略與離線可執行性

**決策**：測試分為兩組，以 pytest marker 區隔。

| 測試組 | 指令 | 相依 | 用途 |
|--------|------|------|------|
| 預設套件 | `pytest -m "not security"` | 無外部服務、無網路、無 Docker | 憲章原則 II 的離線套件；涵蓋所有應用行為 |
| 安全套件 | `pytest -m security` | 本機 Docker | 憲章「安全關卡」；驗證沙箱真實隔離行為 |

預設套件中，Supabase 以本機 PostgreSQL 或記憶體替身取代，AI 與 Email 以介面替身
取代，沙箱以 `FakeSandboxRunner` 取代。

安全套件驗證真實沙箱的三類行為：網路阻斷、資源耗盡中止（CPU／記憶體／pids／
輸出量）、檔案系統存取阻擋。這組測試斷言的是真實容器的行為，替身在此無意義。

**理由**：憲章原則 II 要求測試套件能在無網路、無外部服務環境完整執行；
憲章「安全關卡」要求沙箱變更必須通過真實隔離驗證。兩者並非衝突——前者規範的是
應用行為的驗證方式，後者規範的是安全機制本身的驗證方式。以 marker 區隔可同時滿足，
且預設套件仍完全離線可執行。

RLS 政策的驗證需要真實 PostgreSQL（替身無法驗證資料庫層的拒絕行為），
因此列入預設套件但以本機 PostgreSQL 執行——PostgreSQL 為本機程序而非網路服務，
不影響離線可執行性。

**已評估的替代方案**：

- **全部使用替身**——RLS 與沙箱是本系統兩個最關鍵的安全機制，
  以替身驗證等於沒有驗證。
- **全部使用真實服務**——預設套件將無法離線執行，牴觸憲章原則 II。
