# 功能規格：面試官簡易出題頁

**功能分支**：`003-manager-quick-ask`

**建立日期**：2026-08-03

**狀態**：已實作

**輸入**：「只需要一個題目輸入框（多行文字）加一個送出按鈕，讓面試官輸入題目後送出給受試者。
視覺風格沿用應徵者作答頁，畫面盡量簡化。」

**上游規格**：[001](../001-ai-recruitment-assessment/spec.md) FR-023～FR-028（出題與指派）、
[002](../002-candidate-assessment-ui/spec.md)（應徵者介面與設計系統）。
本功能**不新增任何後端行為**，只是既有 `assign-question` 端點的一個更輕的入口。

## 背景

既有的主管介面 `frontend/manager.html` 功能完整（題庫挑題、AI 生成、草稿編輯、審閱決策），
但要「快速丟一道自己想好的題目給某位應徵者」時，路徑偏長。本功能提供一個最小入口：
打字、選人、送出。

它是**額外入口，不取代**既有主管介面。

## 使用者情境與測試

### 使用者故事 1 — 面試官快速出題（優先級：P1）

面試官打開頁面，從清單挑一位待指派的應徵者，把想好的題目直接打進一個輸入框，按送出。
應徵者開啟原本收到的專屬連結就會看到這道題目。

**獨立測試方式**：「一段文字 → 後端要的 Question」是本頁唯一的判斷邏輯，為純函式，
可於無瀏覽器環境驗證；其餘為既有 API 的呼叫。

**驗收情境**：

1. **Given** 面試官已提供有效權杖，**When** 頁面載入，**Then** 顯示所屬部門中
   狀態為「待指派題目」的應徵者清單。
2. **Given** 面試官輸入多行題目，**When** 送出，**Then** 第一行成為題目標題、
   其餘成為題目敘述，並寫入該筆考核的題目快照。
3. **Given** 送出成功，**When** 應徵者開啟其專屬連結，**Then** 看到該題目與範例測資，
   狀態為「待應徵者作答」。
4. **Given** 輸入框為空白，**When** 送出，**Then** 顯示提示且**不發出任何請求**。
5. **Given** 工程類職缺且未填測資，**When** 送出，**Then** 顯示後端回傳的
   「必須補齊測試案例」訊息，考核狀態不變（上游 FR-026）。
6. **Given** 沒有任何待指派的應徵者，**When** 頁面載入，**Then** 顯示說明為何清單為空，
   並停用送出按鈕。
7. **Given** 權杖無效或過期，**When** 載入清單，**Then** 回到權杖輸入畫面並說明原因。
8. **Given** 送出請求進行中，**When** 面試官再次按送出，**Then** 不得送出第二次請求
   （指派會改變狀態，第二次必定得到 409）。

## 需求

### 功能需求

- **FR-201**：頁面位於 `frontend/manager/ask.html`，網址為 `/manager/ask.html`。
- **FR-202**：畫面為單張置中卡片，只含：應徵者選單、題目輸入框、範例測資兩欄、送出按鈕。
- **FR-203**：送出必須呼叫既有的 `POST /manager/assessments/{id}/assign-question`，
  **不得**新增後端端點、不得寫入任何前端 mock 資料來源。
- **FR-204**：所有 API 呼叫一律經由 `frontend/js/api.js`。
- **FR-205**：題目文字的第一行為標題（上限 200 字元，超過即截斷），其餘為敘述；
  只有一行時標題與敘述相同。開頭的空行自動略過。
- **FR-206**：難度以「中等」送出；**不得**填寫 `source`（面試官手打的題目既非題庫題
  亦非 AI 生成，硬填等於在題目快照裡謊報來源），亦不填 `language`
  （應徵者作答頁本就有語言選擇）。
- **FR-207**：範例測資兩欄皆空時不產生測資；前端**不得**自行補佔位測資——
  假測資會讓自動評測的正確性維度失去意義。
- **FR-208**：清單只列出狀態為「待指派題目」的考核；其餘狀態送出必被後端以 409 擋下。
- **FR-209**：視覺必須與應徵者作答頁一致，且一致性**必須**來自共用樣式表，
  不得以複製色碼達成。
- **FR-210**：送出中必須停用送出按鈕。
- **FR-211**：失敗訊息必須可行動。後端自己的訊息（缺測資、狀態不符）原樣呈現；
  無後端訊息時，至少要能區分「權杖問題」「網址／來源問題」「後端沒開」三類。
  （與應徵者頁相反：那裡對外，訊息一律取自本地字串表；這裡對內，越具體越好。）
- **FR-212**：API 回應 404 時，必須指出最可能的原因是「頁面被開在只提供靜態檔的
  伺服器上」。這是實際發生過的事故：頁面能開、API 全 404，而原本的通用訊息
  「請稍後再試」讓使用者完全無從判斷。

### 非功能需求

- **NFR-101**：不修改後端任何程式碼、不修改資料庫結構、不改變既有 API 的安全模型。
- **NFR-102**：不取代或修改既有的 `frontend/manager.html`。
- **NFR-103**：不引入 npm 相依與建置流程。

### 不變條件

- **INV-101**：`frontend/manager/` 內無直接 `fetch(`。
- **INV-102**：`frontend/manager/` 不匯入應徵者模組；應徵者模組不匯入 `manager` 相關模組。
- **INV-103**：`frontend/manager/` 自 `api.js` 匯入的識別字在允許清單內
  （`manager`、`getAuthToken`、`setAuthToken`、`ApiError`）。
- **INV-104**：`/manager/assessments` 等 API 路由不被新增的 `frontend/manager/` 靜態目錄遮蔽。
- **INV-105**：`frontend/manager/css/ask.css` 不得出現任何寫死色碼或色票變數定義。
- **INV-106**：`ask.js` 查找的每個 element id 都存在於 `ask.html`。
- **INV-107**：`frontend/manager/core/` 不引用瀏覽器 API。

## 題目如何傳遞給應徵者

不需要 mock，也不需要新的資料通道。既有流程原本就打通：

```text
面試官 ask.html
   │  POST /manager/assessments/{id}/assign-question   （既有端點，需 Manager JWT）
   ▼
後端 assign_question
   ├─ 寫入 assessments.question_snapshot（題目快照，FR-028）
   ├─ 狀態 PENDING_ASSIGN → PENDING_CANDIDATE（FR-074）
   └─ 寫入 audit_logs：QUESTION_ASSIGNED（FR-077）
   ▼
應徵者 candidate/assessment.html
      GET /candidate/session/{token}  →  回應中的 question 欄位
```

**應徵者作答頁一行都不用改**：它本來就從 `GET /candidate/session/{token}` 讀 `question`，
且該回應會自動濾掉隱藏測資（上游 FR-054、spec 002 FR-132）。

## 已知限制

- **沒有登入頁**：本專案至今沒有任何取得 JWT 的介面（`setAuthToken` 有匯出但無人呼叫）。
  本頁提供一個貼上權杖的欄位作為權宜之計，權杖存於 `localStorage`，與既有主管介面共用。
  正式的登入流程不在本功能範圍。
- **demo 資料的部門錯配**：demo 種子中唯一「待指派題目」的考核（陳小雯／前端工程師）
  屬 DESIGN 部門，而 `demo-manager-user` 的 `dept_id` 為 ENG。以 ENG 權杖開啟本頁
  會看到空清單——這是部門隔離（上游 FR-003）正確運作的結果，不是缺陷。
  demo 驗證請使用 `dept_id: DESIGN` 的權杖。

## 範圍外

- 登入流程、題庫挑題、AI 生成題目、審閱與決策（既有主管介面已涵蓋）。
- 多題組卷、題目編輯與重新指派。
- 修改後端、資料庫結構或 candidate API 的安全模型。
