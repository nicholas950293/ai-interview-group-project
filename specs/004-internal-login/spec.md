# 功能規格：內部人員登入

**功能分支**：`004-internal-login`

**建立日期**：2026-08-03

**狀態**：已實作

**輸入**：使用者問「貼權杖是什麼？」——這個問題揭露了一個從未被實作的需求。

## 背景：一個從未被建的功能

上游 [spec 001](../001-ai-recruitment-assessment/spec.md) 的 **FR-005** 明訂
「HR 與部門主管必須經帳號認證後方能使用系統」，但查證後確認：

- `specs/001-.../tasks.md` 中**沒有任何一項登入相關的任務**
- 後端只**驗證** JWT（`dependencies.py`），沒有任何端點能**發出** JWT
- 前端沒有一行 Supabase Auth 程式碼；`setAuthToken` 有匯出但無人呼叫

也就是說，HR 頁與主管頁自實作以來，唯一的使用方式是**手動把 JWT 塞進
`localStorage`**。[spec 003](../003-manager-quick-ask/spec.md) 的出題頁繼承了這個
缺口，只是加了個貼上欄位讓人不必開 DevTools——那不是解法，是把問題挪到檯面上。

本功能補上 FR-005 真正缺的那一半。

## 使用者情境與測試

### 使用者故事 1 — 內部人員以帳密登入（優先級：P1）

HR 或部門主管開啟系統，輸入 Email 與密碼登入，之後所有頁面都認得他的身分與部門，
不需要接觸任何權杖。

**獨立測試方式**：登入端點可獨立驗證——正確帳密回傳可用的權杖，錯誤帳密回傳 401，
且兩種失敗（帳號不存在／密碼錯誤）的回應完全相同。

**驗收情境**：

1. **Given** 有效帳密，**When** 送出登入，**Then** 回傳權杖與角色、姓名、部門，
   且該權杖可直接用於後續 API。
2. **Given** 密碼錯誤，**When** 送出登入，**Then** 回傳 401。
3. **Given** 帳號不存在，**When** 送出登入，**Then** 回應與「密碼錯誤」**完全相同**。
4. **Given** 密碼正確但該人不在 `internal_users` 中，**When** 送出登入，**Then** 仍回傳
   與前兩者相同的 401——不透露該帳號在認證服務中存在。
5. **Given** 認證服務中斷，**When** 送出登入，**Then** 回傳 503，與憑證錯誤明確區分。
6. **Given** 尚未登入，**When** 開啟任一內部頁面，**Then** 導向登入頁並記住原本要去的位置。
7. **Given** 權杖過期，**When** 呼叫任何 API 得到 401，**Then** 清除權杖並回登入頁。
8. **Given** 已登入，**When** 點選登出，**Then** 清除權杖並回登入頁。

## 需求

### 功能需求

#### 登入端點

- **FR-301**：系統必須提供 `POST /auth/login`，以 Email 與密碼換取存取權杖。
- **FR-302**：密碼**不得**儲存於本系統。驗證一律委由外部認證服務
  （Supabase Auth），與 AI／沙箱／Email 相同，以可替換介面隔離。
- **FR-303**：角色與部門必須來自 `internal_users`——身分的真相來源只有一個，
  不得取自認證服務的 metadata。
- **FR-304**：簽出的權杖必須包含 RLS 政策所讀取的 `app_role` 與 `dept_id` claim，
  以及 PostgREST 所需的 `role: authenticated`。
- **FR-305**：權杖必須有明確效期（預設 8 小時，由 `SESSION_TTL_HOURS` 設定）。
- **FR-306**：權杖**不得**包含姓名或 Email（FR-079：個資不得散布至到處轉發的憑證中）。
- **FR-307**：「帳號不存在」「密碼錯誤」「非內部使用者」三種失敗必須回傳**完全相同**
  的回應。任何差異都是帳號列舉管道。
- **FR-308**：認證服務不可用必須回傳 503，與憑證錯誤（401）明確區分。
- **FR-309**：登入端點本身不得要求 `Authorization` 標頭。

#### 登入頁與各頁整合

- **FR-310**：登入頁位於 `/login.html`，視覺沿用共用設計系統。
- **FR-311**：未登入時，HR 頁、主管頁與出題頁必須導向登入頁，並以 `next` 記住原目的地。
- **FR-312**：登入成功後導向 `next`；`next` **必須**經過驗證僅接受同源絕對路徑，
  否則退回角色預設頁。未驗證的 `next` 會讓登入頁變成釣魚跳板（open redirect）。
- **FR-313**：任何 API 回應 401／403 時，必須清除權杖並回登入頁；
  其餘錯誤**不得**觸發此行為——網址錯或後端沒開，重新登入也解決不了。
- **FR-314**：各頁必須顯示目前登入者，並提供登出。
- **FR-315**：demo 模式才顯示測試帳號提示；正式環境的登入頁**不得**印出任何憑證。

#### 資料庫

- **FR-316**：`internal_users` 必須新增一條 RLS 政策，允許已認證者讀取**自己那一列**。
  這是登入流程的必要條件（見下節），且比既有政策更窄。

### 不變條件

- **INV-201**：登入的三種失敗回應完全相同（狀態碼與內容）。
- **INV-202**：簽出的權杖不含 Email 與姓名。
- **INV-203**：`next` 只接受同源絕對路徑。
- **INV-204**：`frontend/manager/` 自 `api.js` 取用的匯出不含 `hr` 或 `candidate`。

## 為什麼需要新的 RLS 政策

`0009_rls_policies.sql` 的兩條 `internal_users` 政策都以 `app_role()` 為條件：

```sql
internal_users_hr_select    USING (app_role() = 'HR')
internal_users_self_select  USING (app_role() = 'MANAGER' AND auth_user_id = ...)
```

但登入當下，Supabase Auth 剛發出的 token **還沒有** `app_role` claim——那正是我們
要查出來的東西。於是形成雞生蛋：**要先知道角色，才讀得到記錄角色的那一列。**

`0012_internal_users_bootstrap.sql` 打破這個循環：已認證者可讀自己那一列，不需要角色。

它比既有政策更**窄**，不放寬任何跨使用者的存取：條件為
`auth_user_id = app_auth_user_id()`，只可能命中請求者本人；讀到的是自己的姓名、
Email、角色與部門——他本來就知道的資訊；不影響任何其他資料表；`anon` 仍被 0009 擋住。

`InMemoryDataStore` 已同步鏡射此政策，使離線測試仍能斷言權限行為。

## 已知限制與部署前提

- **正式環境需要 Supabase Auth 帳號**：`internal_users.auth_user_id` 必須對應到
  Supabase Auth 中真實存在的使用者。建立內部帳號的流程（誰來建、怎麼建）
  不在本功能範圍。
- **0012 必須先套用**，否則登入會在「查角色」那一步失敗。
- **`SupabaseAuthProvider` 未經真實 Supabase 驗證**：本機沒有 Supabase 實例，
  該實作只經過離線的介面契約測試。首次部署時必須實測。
- **權杖存於 `localStorage`**：與既有頁面一致。若日後要防禦 XSS 竊取權杖，
  應改為 httpOnly cookie，那是獨立的變更。
- **沒有「忘記密碼」與「變更密碼」**：兩者都屬 Supabase Auth 的能力，本功能未接。

## 範圍外

- 建立／停用內部帳號的管理介面。
- 單一登入（SSO）、多因素驗證、忘記密碼。
- 應徵者的身分機制——他們不需要帳號，以連結中的 token 識別（上游 FR-005 後半）。
