# AI 招募與技術考核系統 憲章

## 核心原則

### I. 規格驅動交付（不可妥協）

任何行為變更**必須**源自規格文件。在功能具備以下三份文件之前，**不得**開始開發：載明編號功能需求的
`spec.md`、描述技術方案的 `plan.md`、以及列舉工作項目的 `tasks.md`。每一項任務**必須**可追溯至至少
一個需求編號；若在實作過程中發現新需求，**必須**先將其寫回 `spec.md`，才能合併滿足該需求的程式碼。

理由：本專案的價值來自規格產出物，而非零散的程式碼。無法追溯的變更會讓規格淪為謊言，並摧毀
推論範圍的能力。

### II. 測試優先驗證（不可妥協）

測試**必須**先於其所涵蓋的實作撰寫，**必須**在實作開始前因預期原因而失敗，並**必須**在任務標記完成
前通過。`spec.md` 中的每一個驗收情境**必須**至少對應一項自動化測試。後端測試以 `pytest` 為指定
執行器。只要測試套件中仍有任何失敗，**不得**在 `tasks.md` 中將該任務勾選為完成。

測試套件**必須**能在無網路、無外部服務的環境中完整執行。凡相依於外部服務者，**必須**能以替身
（test double）替換。

理由：評測流程承載的是對真實應徵者具有實際後果的錄用決策。從未被觀察到失敗過的行為，等同於
從未真正被驗證。而一套需要外部服務才能跑的測試，在最需要它的時候（服務中斷、離線開發、CI）
會失效。

### III. 有依據的技術選型與最小範圍

技術棧由「技術與資料限制」章節界定。實作**不得**超出該範圍。任何新增的執行期相依套件、外部
服務或基礎設施元件，**必須**在 `plan.md` 的「技術脈絡」中提出理由，載明其服務的需求編號以及
被否決的較簡單替代方案。

**必須**優先採用能滿足當前規格的最小實作。為預期中的未來需求而建立的臆測性抽象，**必須**在
審查階段移除。規格未要求的功能**不得**實作。

理由：本專案已從純本機模組轉為整合資料庫、AI 服務與沙箱的系統，技術面的複雜度已有既定下限。
正因如此，超出該下限的每一分複雜度都必須被明確辯護——否則系統會在無人察覺的情況下持續膨脹。

### IV. 應徵者資料保護與最小權限

應徵者個人資料**必須**視為敏感資料。存取**必須**依角色強制控管，且該控管**必須**在資料存取層
實施，**不得**僅依賴前端介面隱藏。跨部門、跨角色的越權存取**必須**被拒絕而非僅被隱藏。

以下內容**不得**寫入應用程式日誌：應徵者姓名、Email、電話，以及其提交的程式碼與作答內容。

真實應徵者資料**不得**出現於測試、測試資料、範例檔案或任何進版控的產出物中，**必須**改用合成
資料。任何憑證、API 金鑰與服務連線字串**不得**進入版本控制。

理由：招募系統集中了大量個人資料，一旦外洩將直接傷害應徵者，並為營運方帶來法遵責任。而介面
層的隱藏從來不是存取控制——它只是讓越權變得不明顯。

### V. 可稽核且公平的評估

每一次考核狀態轉換**必須**連同執行者與時間一併記錄。稽核歷程**必須**以獨立的唯附加
（append-only）資料結構實作，**不得**以覆寫狀態欄位的方式替代。更正以新增紀錄呈現，
**不得**改寫或刪除既有紀錄。

評分規則**必須**明確且可檢視，**不得**散落隱藏於偶然的程式路徑中。任何 AI 輔助的評分或排序
**必須**僅具建議性質：最終決策**必須**由真人評測者記錄，系統**必須**同時保存 AI 產出與人類決策，
且**不得**自動產生綜合錄取建議。

理由：錄用結果必須在事後可被解釋與申訴。未經記錄或全自動產生的決策，無法向應徵者、稽核人員
或司法機關辯護。一個會被覆寫的狀態欄位不是歷程，是最新值。

### VI. 不受信任程式碼的隔離執行（不可妥協）

應徵者提交的程式碼是不受信任的輸入。執行它**必須**滿足以下每一項條件，缺一不可：

- **必須**在與應用程式、資料庫及其他應徵者完全隔離的環境中執行
- **必須**禁止對外網路存取
- **必須**施加資源上限，至少涵蓋 CPU 時間、記憶體用量、牆鐘時間、程序數量與輸出大小；
  超限**必須**強制中止
- **必須**以最低權限身分執行，**不得**具備提權能力
- **必須**禁止存取宿主檔案系統，僅允許讀寫該次執行專屬的暫存工作目錄
- 每次執行**必須**使用全新環境，執行結束後**必須**銷毀，**不得**跨執行重用

沙箱不可用時，系統**必須**降級為「接受提交但不執行」，**不得**改以未隔離的方式執行程式碼。
任何放寬上述條件的變更，**必須**在 `plan.md` 中明確載明並附上風險評估。

理由：這是本系統唯一會執行外部人員所撰寫程式碼的地方，也是唯一一處單次失誤即可導致資料庫
外洩或主機淪陷的位置。此處沒有「先求能動、之後再補安全」的空間——不安全的執行環境比沒有
執行功能更糟。

## 技術與資料限制

- **後端**：Python 3.11 以上，以 FastAPI 提供 API 服務。非同步 I/O 用於外部服務呼叫。
- **資料庫**：Supabase (PostgreSQL)。資料表結構**必須**以版本控管的遷移檔定義，
  **不得**僅存在於管理介面中。
- **AI 服務**：Google Gemini API，用於出題、答題助教與自動評測。
- **前端**：HTML5 + Tailwind CSS + JavaScript。具體框架選擇由 `plan.md` 決定並記錄。
- **沙箱**：具作業系統層隔離能力的容器化執行環境，滿足原則 VI 的全部條件。
- **相依範圍**：上述以外的執行期相依**必須**依原則 III 提出理由後方可加入。
- **外部服務隔離**：所有外部服務呼叫（資料庫、AI、郵件、沙箱）**必須**置於可替換的介面之後，
  使測試套件得以在無網路環境下完整執行。
- **專案結構**：由 `plan.md` 決定並明確記錄。測試**必須**與正式程式碼分離。
- **跨平台**：開發環境**必須**能在 Windows、macOS 與 Linux 上運作；**不得**寫死平台專屬
  路徑或 shell 呼叫。沙箱本身為容器化元件，不受此限。
- **設定與機密**：所有環境相關設定**必須**由環境變數提供，**不得**寫死於程式碼。

## 開發流程與品質關卡

1. **規格（Specify）**——由 `spec.md` 定義需求與驗收情境；模糊之處須在規劃前釐清。
2. **規劃（Plan）**——由 `plan.md` 記錄技術方案並通過「憲章檢查」，該檢查**必須**列出每一項
   受影響的原則，並說明如何達成合規。
3. **任務（Task）**——由 `tasks.md` 將計畫拆解為具相依順序、可個別驗證的項目。
4. **實作（Implement）**——先測試、後程式碼，一次處理一項任務。唯有測試通過才可勾選任務。
5. **分析（Analyze）**——在功能宣告完成前，**必須**驗證 `spec.md`、`plan.md` 與 `tasks.md`
   三者的一致性。

功能宣告完成前**必須**成立的關卡：

- 完整測試套件通過，且該套件可在無網路環境下執行。
- `spec.md` 中每一項功能需求皆對應到已完成的任務與通過的測試。
- `tasks.md` 中沒有任何任務在缺少對應實作的情況下被勾選。
- **安全關卡**：涉及沙箱的變更**必須**通過隔離驗證，至少涵蓋網路阻斷、資源耗盡中止、
  檔案系統存取阻擋三類測試。
- **權限關卡**：涉及角色存取的變更**必須**有對應的越權嘗試測試，且該測試驗證的是資料存取層
  的拒絕行為。
- 任何偏離原則之處皆已記錄於 `plan.md` 並附上理由。

## 治理

本憲章的效力**優先於**本儲存庫中任何相衝突的作法、慣例與個人偏好。當工具、樣板或既有習慣與
此處所述原則衝突時，以原則為準。

**修訂程序**：修訂**必須**透過 `/speckit-constitution` 流程更新本檔案。每次修訂**必須**載明版本
變動、在本檔案頂端的同步影響報告中記錄變更內容，並指出需回頭補正合規性的進行中工作。
**不得**將修訂作為功能開發的附帶產物。

**版本政策**：本文件遵循語意化版本規範。

- **MAJOR**——移除某項原則，或以使原有合規成果失效的方式重新定義原則。
- **MINOR**——新增原則或治理章節，或實質擴充既有規範。
- **PATCH**——不改變義務內容的釐清、措辭與格式調整。

**合規審查**：憲章合規性**必須**於規劃階段檢查一次，並在功能宣告完成前再檢查一次。違規將阻擋
功能完成，直到違規被修正，或於 `plan.md` 中載明為明確且具理由的例外（須指名所涉原則與理由）。
未經記載的例外一律視為缺陷。原則 II 與原則 VI 標示為不可妥協，**不得**以例外方式繞過。
